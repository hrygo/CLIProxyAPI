# v8.0.51 replay spike

Status: **not accepted**. The candidate starts at upstream release v8.0.51
(`7cad1cb7df48c6c5ffb7ff0b34ef8198806115bc`). Fork changes are recorded as
focused commits on `codex/upstream-v8051-replay`; this branch does not replace
fork `main` or establish a new accepted upstream baseline.

## Origin of the Gemini stream behavior

The fork's `47b61ca0` added a wait after a finish without same-frame usage to
retain usage sent separately. The locally running release at source revision
`415b85360ab9c883efe5598e5b94cf08a7f214b3` contains that behavior. Its
usage-only tail does not itself end the response; the executor also filters
the native Gemini `[DONE]` marker and synthesizes it only at clean EOF.
Consequently, a provider that keeps the connection open can leave the client
waiting. This is a source-level finding, not evidence that a production request
encountered that sequence.

Upstream also contains a related wait in `5ec31442`, present in the v8.0.51
release; the two commits are not ancestors of one another, and their history
does not establish whether one implementation drew on the other. Upstream's
native Gemini marker filtering predates both, and its Responses mapping also
omits `toolUsePromptTokenCount` from client-facing input usage. The internal
usage parser already includes that field, so the omission is specific to the
Responses mapping. Neither behavior was introduced by replaying the fork onto
v8.0.51.

## Gemini usage boundary

After a finish frame, the Responses terminal is sent without waiting for later
usage. A complete usage frame sent after finish can therefore be absent from
both the client terminal and internal accounting; even frames already buffered
by the reader can be missed. A later signature or grounding frame can also be
missed, and a subsequent tool turn may lack its native signature. Same-frame
usage, signatures and grounding are retained. The maintainer explicitly chose
prompt completion with these limitations and deferred candidate acceptance.
The accounting record's integer fields cannot distinguish unknown counts from
zero; a partial observation can therefore be reported as a complete-looking
lower count and must not be treated as an authoritative total.

An opportunistic read of already-buffered SSE frames could capture some later
frames, but cannot establish whether another update will arrive in a later
read. It would also need to preserve the per-frame translation and plugin
hooks. A complete client-facing result and prompt completion cannot both be
guaranteed without additional upstream finality information or a change to the
completion contract.

The [Gemini API documentation](https://ai.google.dev/api/generate-content)
describes the metadata fields but does not identify a final usage snapshot.
The [Google Gen AI Python SDK](https://github.com/googleapis/python-genai/blob/main/google/genai/_extra_utils.py)
treats streamed usage as an updated running total. Neither field presence nor
the first usage frame is evidence that further updates cannot arrive.

## Remaining limits

- Devin rejects unknown protobuf fields while a tool contract is active, and
  rejects multiple native custom-output history that cannot be restored
  losslessly from the protobuf.
- Home bridge continuation tests cover both resending and omitting `tools`;
  omission is not automatically inherited. A live CLIProxyAPIHome deployment
  was not verified. The unconsumed-terminal drain test applies backpressure at
  the Manager channel; it does not establish that a blocked downstream socket
  write or every source/drainer goroutine has exited when drain returns.
- A read-only local process inspection on 2026-11-05 found the running
  CLIProxyAPI instance had not enabled its Home integration, and found no
  separate process named CLIProxyAPIHome. This does not establish whether a
  renamed process or a deployment on another host exists.
- All provider and WebSocket evidence uses isolated local fixtures; no new
  real-client, real-provider, release, deployment, or performance claim follows.
